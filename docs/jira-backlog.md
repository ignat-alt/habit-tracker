# Habit Tracker — бэклог для Jira (Практика 1)

Готовые тексты для копирования в Jira. Проекты: **HT** (Scrum) и **HTK** (Kanban).
Компоненты в обоих проектах: Backend, Frontend, Mobile, QA, DevOps.

## Эпики (5)

| Эпик | Название |
|---|---|
| E1 | Аутентификация и профиль |
| E2 | Backend API «Привычки» |
| E3 | Веб-дашборд |
| E4 | Мобильное приложение |
| E5 | Инфраструктура и качество |

## Распределение по проектам

- **HT (Scrum):** задачи 1–12 (эпики E1–E3).
- **HTK (Kanban):** задачи 13–19 (эпики E4 и E5) + hotfix №20 по ходу занятия.

Обоснование: у эпиков E1–E3 есть жёсткие зависимости (фронту нужен API, API нужна авторизация), поэтому их удобно планировать спринтом с целью. Мобильные задачи, инфраструктура и тесты — поток разнотипных задач без чёткой последовательности, а hotfix вообще нельзя заранее запланировать.

## Истории

### E1. Аутентификация и профиль

**HT-1 · Backend · 3 SP** — Как пользователь, я хочу зарегистрироваться по email и паролю, чтобы иметь личный аккаунт.
1. POST /auth/register создаёт пользователя и возвращает 201.
2. Повторная регистрация с тем же email возвращает 409.
3. Пароль хранится только в виде хэша.

**HT-2 · Backend · 3 SP** — Как пользователь, я хочу войти в систему, чтобы получить доступ к своим привычкам.
1. POST /auth/login с верными данными возвращает JWT-токен.
2. Неверный пароль возвращает 401.
3. Токен истекает через заданное время.

**HT-3 · Frontend · 2 SP** — Как пользователь, я хочу просматривать и редактировать профиль, чтобы менять свои данные.
1. Страница профиля показывает имя и email.
2. Изменения сохраняются и отображаются после перезагрузки.
3. Пустое имя не принимается, показывается ошибка.

**HT-4 · Backend · 2 SP** — Как пользователь, я хочу восстановить пароль по email, чтобы вернуть доступ к аккаунту.
1. POST /auth/forgot отправляет письмо со ссылкой.
2. Ссылка действует ограниченное время.
3. После смены пароля старые токены перестают работать.

### E2. Backend API «Привычки»

**HT-5 · Backend · 5 SP** — Как backend-разработчик, я хочу реализовать CRUD-эндпоинты для сущности «Привычка», чтобы клиентские приложения могли создавать, читать, изменять и удалять привычки пользователя.
1. POST /habits создаёт привычку и возвращает 201.
2. GET /habits/{id} возвращает 404 для несуществующего id.
3. DELETE /habits/{id} требует авторизации владельца.

**HT-6 · Backend · 3 SP** — Как пользователь, я хочу отметить выполнение привычки за день, чтобы вести учёт.
1. POST /habits/{id}/checkins добавляет отметку.
2. Две отметки за один день не дублируются.
3. Чужую привычку отметить нельзя (403).

**HT-7 · Backend · 5 SP** — Как пользователь, я хочу видеть серию (streak) и статистику, чтобы понимать свой прогресс.
1. GET /habits/{id}/streak возвращает текущую серию.
2. Пропуск дня обнуляет серию.
3. Серия ограничена 365 днями.

**HT-8 · Backend · 2 SP** — Как разработчик клиента, я хочу единый формат ошибок и валидацию запросов, чтобы одинаково обрабатывать ошибки.
1. Некорректный JSON возвращает 422.
2. Все ошибки имеют вид {"detail": "..."}.
3. Ошибки валидации не раскрывают внутренние детали.

### E3. Веб-дашборд

**HT-9 · Frontend · 3 SP** — Как пользователь, я хочу страницу входа и регистрации, чтобы попасть в приложение.
1. Форма валидирует email и пароль до отправки.
2. После входа токен сохраняется и открывается дашборд.
3. Ошибки сервера показываются понятным текстом.

**HT-10 · Frontend · 5 SP** — Как пользователь, я хочу видеть список привычек с добавлением и редактированием, чтобы управлять ими.
1. Список показывает все привычки с текущей серией.
2. Форма добавления создаёт привычку без перезагрузки страницы.
3. Привычку можно изменить и удалить с подтверждением.

**HT-11 · Frontend · 5 SP** — Как пользователь, я хочу график прогресса по привычке, чтобы видеть динамику.
1. График показывает отметки за последние 30 дней.
2. При отсутствии данных показывается пустое состояние.
3. График обновляется после новой отметки.

**HT-12 · Frontend · 3 SP** — Как пользователь, я хочу пользоваться дашбордом на телефоне, чтобы открывать его с любого устройства.
1. Вёрстка корректна при ширине 360 px.
2. Нет горизонтальной прокрутки.
3. Кнопки удобны для нажатия пальцем.

### E4. Мобильное приложение

**HT-13 → HTK-1 · Mobile · 3 SP** — Как пользователь, я хочу экран быстрой отметки, чтобы отмечать привычки в один тап.
1. Все привычки на сегодня на одном экране.
2. Тап отмечает привычку выполненной.
3. Повторный тап отменяет отметку.

**HTK-2 · Mobile · 5 SP** — Как пользователь, я хочу push-напоминания, чтобы не забывать о привычках.
1. Время напоминания настраивается для привычки.
2. Уведомление приходит в заданное время.
3. Выполненную привычку не напоминаем.

**HTK-3 · Mobile · 3 SP** — Как пользователь, я хочу синхронизацию с сервером, чтобы данные были одинаковы в вебе и на телефоне.
1. Отметка в приложении видна в вебе.
2. Без сети отметки сохраняются локально и отправляются позже.
3. При конфликте побеждает более поздняя отметка.

### E5. Инфраструктура и качество

**HTK-4 · DevOps · 2 SP** — Как разработчик, я хочу инициализированный репозиторий со структурой проекта, чтобы команда начала работать одинаково.
1. Есть backend/, web/, README.md, .gitignore.
2. Защищена ветка main.
3. Описано правило именования веток (HT-5-crud-habits).

**HTK-5 · DevOps · 2 SP** — Как разработчик, я хочу раздельные dev/prod конфигурации, чтобы не смешивать окружения.
1. Секреты берутся из переменных окружения, а не из кода.
2. Есть .env.example без реальных значений.
3. Prod и dev отличаются хотя бы адресом БД и режимом отладки.

**HTK-6 · QA · 3 SP** — Как QA-инженер, я хочу набор тестовых сценариев для API, чтобы автоматически ловить регрессии.
1. Покрыты успешные и ошибочные ответы всех эндпоинтов.
2. Тесты запускаются одной командой.
3. Покрытие не ниже 80%.

**HTK-7 · QA · 2 SP** — Как QA-инженер, я хочу чек-лист ручного тестирования дашборда, чтобы проверять релиз перед выпуском.
1. Чек-лист покрывает вход, список, график, мобильную вёрстку.
2. Для каждого пункта указан ожидаемый результат.
3. Есть колонка для отметки «пройдено / не пройдено».

**HTK-8 (hotfix №20) · Mobile · 2 SP** — Как пользователь, я хочу, чтобы приложение не падало из-за устаревших push-токенов, чтобы напоминания не терялись.
1. Токен, который сервер пометил недействительным, удаляется из базы.
2. Остальные токены продолжают получать уведомления.
3. Событие записывается в лог.

> Сумма SP по проекту HT: 3+3+2+2+5+3+5+2+3+5+5+3 = **41 SP**.
> Сумма SP по HTK: 3+5+3+2+2+3+2+2 = **22 SP**.

## Задание 3 — Scrum: спринт

**Sprint 1 · 2 недели · цель:** «Реализовать регистрацию/вход и базовый CRUD привычек, вывести список привычек в вебе».

Взяты в спринт (**18 SP**, условная velocity команды 18):

| Задача | SP | Компонент |
|---|---|---|
| HT-1 Регистрация | 3 | Backend |
| HT-2 Вход (JWT) | 3 | Backend |
| HT-5 CRUD привычек | 5 | Backend |
| HT-8 Валидация и формат ошибок | 2 | Backend |
| HT-9 Страница входа и регистрации | 3 | Frontend |
| HT-3 Профиль | 2 | Frontend |

Итого: 3+3+5+2+3+2 = 18.

### Имитация хода спринта

| Статус | Задача | Комментарий «от исполнителя» |
|---|---|---|
| Done | HT-1 | «Эндпоинт готов, пароль хэшируется, тесты на 201 и 409 зелёные.» |
| Review/Testing | HT-2 | «JWT выдаётся, жду ревью по сроку жизни токена.» |
| In Progress | HT-5 | «Реализованы POST и GET, дописываю PUT и DELETE.» |
| In Progress | HT-9 | «Форма входа готова, регистрация в работе.» |

### Блокер

HT-9 помечена флагом **blocked**.
- Причина (комментарий): «Нет рабочего /auth/login на dev-стенде, форме нечего вызывать.»
- Решение тимлида: попросить Backend-разработчика выкатить HT-2 на dev в приоритете, а Frontend на это время подключить mock-ответ и взять HT-3. Блокер снят на второй день.

### Ретро

- **Что прошло хорошо:** чёткая цель спринта, бэклог с критериями приёмки, быстро нашли причину блокера.
- **Что не получилось:** Frontend ждал Backend, оценки HT-5 не хватило (задача оказалась объёмнее 5 SP).
- **Что изменим:** договориться об API-контракте (Swagger) до начала спринта; крупные истории резать на части; брать в спринт на 10–15% меньше SP.

## Задание 4 — Kanban: поток

Столбцы: Backlog → To Do → In Progress → Review → Done.
WIP-лимиты: **In Progress ≤ 2, Review ≤ 2**.

Порядок протягивания:

| Шаг | Что происходит |
|---|---|
| 1 | HTK-4 и HTK-5 переходят в In Progress (2/2). Лимит достигнут, HTK-6 не берём. |
| 2 | HTK-4 уходит в Review, освобождается место, берём HTK-6. |
| 3 | HTK-4 в Done. HTK-5 в Review (Review 1/2). |
| 4 | **Внеплановый hotfix HTK-8** добавляется в Backlog. Тимлид ставит его первым: HTK-5 в Done, hotfix сразу в In Progress. |
| 5 | HTK-8 в Review, затем в Done. HTK-6 в Review, затем в Done. |
| 6 | В In Progress берём HTK-7, потом в Done. |

Итог: через доску прошло 5 задач (HTK-4, HTK-5, HTK-8, HTK-6, HTK-7), лимиты не нарушались.

## Задание 5 — Сравнительный анализ

| Вопрос | Ответ |
|---|---|
| Что было проще спланировать — спринт или поток? | Спринт: есть цель, ёмкость в SP и фиксированный набор задач, понятно, что считать успехом. Поток проще запускать (не нужен план), но сложнее оценить, сколько будет сделано к дате. |
| Где сложнее было среагировать на внеплановую задачу? | В Scrum: новую задачу нельзя просто добавить в спринт, не сняв другую (иначе ломается цель и ёмкость). В Kanban hotfix просто встал в начало очереди, и перестраивать ничего не пришлось. |
| Какую методологию выбрали бы для всего проекта и почему? | Основной проект (фичи с зависимостями: авторизация, API, веб) вести по Scrum. Поддержку, багфиксы и инфраструктуру вести потоком Kanban. На практике это гибрид (Scrumban), потому что у Habit Tracker есть оба типа работы. |
