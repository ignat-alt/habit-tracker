## Часть 2. Тексты для сдачи

### Практика 3, задание 8: что вызвало конфликт

Две ветки (`streak-cap` и `streak-log`) отходили от одной версии функции и обе поменяли её последнюю строку `return`: одна на `return min(streak, 365)`, другая добавила `print(...)` перед `return streak`. Первую ветку слили чисто, а при слиянии второй Git увидел, что одна и та же строка изменена по-разному, и не смог выбрать сам. Я вручную объединил обе идеи: сначала `streak = min(streak, 365)`, затем `print`, затем `return streak`, удалил маркеры `<<<<<<<`, `=======`, `>>>>>>>`, сделал `git add` и `git commit`.

### Практика 3, задание 9: конфликт при rebase

Конфликт возник в строке сигнатуры функции: в одной ветке добавили type hints, в другой переименовали параметр. Механика разрешения та же, что при merge (правка файла, `git add`), но завершается командой `git rebase --continue`, а не `git commit`. По ощущениям rebase «переигрывает» мои коммиты по одному поверх main, поэтому конфликт разрешается на моём коммите, а история в итоге получается линейной, без merge-коммита.

### Практика 4, задание 9: рефлексия

- **CI и CD:** CI — это автоматическая проверка кода (тесты, линтер) при каждом push и PR. CD — автоматическая доставка уже проверенного кода на сайт без ручных шагов.
- **Почему deploy зависит от test через `needs`:** без `needs` job'ы идут параллельно, а не по порядку в файле, поэтому деплой мог бы стартовать одновременно с тестами и не ждать результата.
- **Что будет без `needs`:** сломанный код попадёт на рабочий сайт, даже если тесты красные, и пользователи увидят баг.

### Практика 5, задание 13: рефлексия

- **Матрица или копии job'ов:** матрица — это один job, который сам запускается на нескольких версиях Python. Не надо копировать код, а при изменении правим одно место, а не три.
- **Почему `paths` на `pull_request` опасен:** если PR не затронул нужные папки, workflow не запускается, а ruleset требует проверки. Они навсегда зависнут в статусе «Waiting for status» и заблокируют слияние.
- **Почему Tunnel не годится для деплоя из Actions:** runner в Actions временная машина и исчезает после job'а вместе с тоннелем. Адрес быстрого тоннеля к тому же меняется при каждом запуске и аптайма нет.

## Часть 3. Что я не смог сделать и как сделать это вам

Я работаю в закрытой песочнице: у меня нет ваших аккаунтов и нельзя ничего вводить от вашего имени. Вот что осталось, по шагам.

### A. Jira (практика 1)

1. Зайдите на atlassian.com/software/jira → Get it free → зарегистрируйтесь.
2. Создайте сайт, например `habit-tracker-ivanov.atlassian.net`.
3. Create project → Team-managed → шаблон **Scrum**, ключ **HT**. Потом ещё один проект, шаблон **Kanban**, ключ **HTK**.
4. В каждом проекте: Project settings → Features → Estimation → Story points. Project settings → Components → добавьте Backend, Frontend, Mobile, QA, DevOps.
5. Откройте `docs/jira-backlog.md`. Для каждой истории нажмите Create, выберите тип Story, вставьте заголовок, описание (формулировку + критерии приёмки), выберите компонент и впишите SP. Сначала создайте 5 эпиков.
6. Backlog → Create sprint → задайте цель → перетащите 6 задач из плана (18 SP) → Start sprint. Дальше двигайте карточки по плану и пишите комментарии из файла.
7. Скриншоты для сдачи: бэклог, доска HT после завершённого спринта, доска HTK с видимыми WIP-лимитами.

### B. GitHub (практики 4–5)

1. Зарегистрируйтесь на github.com → New repository → имя `habit-tracker`, **пустой**, без README.
2. Скачайте мою папку `habit-tracker` (архив рядом с этим файлом), откройте в ней терминал и выполните:
   ```bash
   git remote add origin https://github.com/ВАШ_ЛОГИН/habit-tracker.git
   git branch -M main
   git push -u origin main
   ```
3. В `README.md` замените `<ваш_логин>` на свой логин и сделайте коммит.
4. Чтобы Pull Request были «по-настоящему» (требование курса), следующие правки делайте через ветку: `git switch -c feature/что-то`, коммит, `git push -u origin feature/что-то`, на GitHub нажмите Compare & pull request → Merge.
5. Ruleset (задание 11): Settings → Rules → Rulesets → New branch ruleset → `protect-main` → Active → Include default branch → включите «Require a pull request» и «Require status checks», добавьте `lint`, `test (3.10)`, `test (3.11)`, `test (3.12)`. Работает только в публичном репозитории.

### C. Cloudflare Pages (практика 4)

1. Зарегистрируйтесь на dash.cloudflare.com → Workers & Pages → Create → Pages → Upload assets → имя `habit-tracker` → перетащите `index.html` и `style.css` из папки `web/`.
2. Account ID виден справа в разделе Workers & Pages. Токен: My Profile → API Tokens → Create Token → шаблон «Edit Cloudflare Workers».
3. В GitHub: Settings → Secrets and variables → Actions → New repository secret: `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`.
4. Если Cloudflare вы не делаете, удалите job `deploy` из конца `ci-cd.yml`, иначе он будет падать.

### E. Cloudflare Tunnel (задание 5, практика 5)

Из песочницы это невозможно (нужен ваш компьютер и телефон). У себя:

1. Установите cloudflared (команды в методичке для вашей ОС).
2. Терминал 1: `uvicorn app.main:app --port 8000` (из папки `backend` с активным venv).
3. Терминал 2: `cloudflared tunnel --url http://localhost:8000`.
4. Найдите в выводе адрес `https://….trycloudflare.com`, откройте его с телефона на мобильном интернете и сделайте скриншот `/docs`.
5. В конце нажмите Ctrl+C в обоих терминалах.
